# Oteryn Atlas comprehensive verification platform

Lifecycle authority: Oteryn/Oteryn-Atlas#85

Design base: `main` at `66f15b463df8668398f2df8e59cf76b95af5741b`.

## 1. Purpose

Oteryn Atlas must treat executable verification as part of implementation, not as a later clean-up phase.

Every shipped behavior must be deeply covered by the tests that are appropriate to that behavior. A feature is not proven by the existence of code, a visible control, a DOM node, a non-zero renderer counter, or one happy-path browser action. The verification platform must prove observable behavior, important invariants, integration boundaries, state transitions, failure behavior, rendering correctness, and performance/stability characteristics where those are material to the change.

There is no separate user-facing module status system. The evidence is the executable suite and its exact-head results.

Every reproducible bug discovered by a user, agent, audit, CI, or live acceptance must leave a permanent deterministic regression test before the bug is considered fixed. The preferred repair sequence is:

1. reproduce the defect;
2. add a test that fails for the defect for the right reason;
3. fix the implementation;
4. prove the new test and the applicable existing suite pass;
5. retain the regression permanently.

## 2. Authority and safety boundaries

Oteryn-Game remains canonical World/Content authority. Atlas tests may use authoritative Game-derived publication products, accepted repository fixtures, or explicitly pinned evidence. Tests must never invent Game-owned coordinates, floors, identity, ordering, roles, semantics, or content merely to make an assertion possible.

Legacy Tibia/OTBM/OTB/SPR/DAT inputs remain migration/reference evidence only and must not become browser-runtime or test fallback authority.

Testability code may expose truthful read-only diagnostics from the actual runtime. It must not:

- change camera, map, layer, creature, animation, publication, or navigation semantics;
- bypass normal data loading;
- inject privileged product state;
- become a second source of truth;
- make production behavior different solely so a test can pass.

## 3. Existing baseline to preserve

This platform extends the repository's existing verification systems rather than introducing a disconnected replacement.

Current baseline includes:

- deterministic JavaScript contracts using `node:test` under `tests/**`;
- browser semantic/runtime contracts such as `tests/browser-semantic.mjs`, `tests/pixel-store.mjs`, `tests/gui-contract.mjs`, `tests/animation-runtime.mjs`, `tests/browser-proof.mjs`, and feature-specific contracts such as `tests/npc-markers.mjs`;
- the Dockerized Playwright/Chromium E2E harness under `e2e/**` delivered through Issue #55 and PR #56/#66;
- strict Playwright runtime/network/page-error capture, failure traces, screenshots and video;
- exact checkout-overlay and exact deployed-preview qualification modes;
- CI jobs and required `atlas-gate`/`provenance-gate` protection;
- FullWorld/browser/WebGL proofs and dedicated feature workflows;
- merged-main/live Synology acceptance with revision qualification.

The platform must consolidate these into a coherent verification architecture and fill the gaps rather than duplicating them.

## 4. Verification principles

### 4.1 Behavior coverage over file coverage

Line/function/branch coverage metrics are useful diagnostics, but they are not the definition of completeness. The primary requirement is coverage of shipped behavior and its risk surface.

For pure critical logic, branch coverage should be measured and driven as high as practical, with critical coordinate/state/contract branches expected to have explicit positive and negative cases. A 100% line-coverage number must never substitute for missing behavior tests.

### 4.2 Independent oracles

A test must not calculate its expected answer exclusively through the same implementation path that produces the actual answer.

Examples:

- a map projection test should compare the production result with an independent reference calculation or invariant, not call `worldToScreen()` twice;
- a renderer synchronization test should compare independently observed base-layer and overlay movement, not only assert both read the same camera object;
- a visual test should not replace geometry verification when exact transforms can be measured;
- a data-contract test should validate against schema/provenance facts, not against a second copy generated by the same faulty compiler path.

Where a failure mode can survive one oracle, use two complementary oracles. Geometry-sensitive rendering should normally combine state/matrix evidence with screen/render evidence.

### 4.3 Determinism first

Use stable browser/container versions, fixed viewport/DPR/locale/timezone, explicit target revision, bounded polling, deterministic fixtures, seeded action generation, and zero hidden retries.

Randomized tests must always print and retain the seed and exact action sequence. A random failure that cannot be replayed is an incomplete test implementation.

### 4.4 First failure remains visible

Retries must not convert a real first-run failure into green acceptance. The normal deterministic suite keeps retries at zero. If infrastructure-level retry is ever justified separately, first-failure evidence and retry classification must remain explicit.

### 4.5 Flakiness is a defect

Tests must not be permanently quarantined because they are intermittent. Repeated scheduled execution is used to discover race conditions and flakes; once reproduced, the race/flake must receive a deterministic or seed-replay regression whenever technically possible.

## 5. Platform layers

### 5.1 Logic, unit, parser and contract tests

Use the existing `node:test` approach by default.

Applicable changes should cover:

- pure transforms and calculations;
- URL/deep-link parsing and serialization;
- state reducers/state machines;
- data normalization and validation;
- publication schemas and version compatibility;
- Game->Atlas boundary constraints;
- invalid/malformed/partial input;
- cache/eviction logic where pure logic exists;
- role/filter/search matching;
- animation scheduling/state logic where pure logic exists;
- boundary values and off-by-one behavior.

Do not introduce another unit-test framework merely for syntax preference.

### 5.2 Property, metamorphic and invariant tests

Coordinate, viewport, floor and zoom logic is especially suitable for generated tests.

Required classes of invariant include where applicable:

- `screenToWorld(worldToScreen(p))` returns `p` within the declared numerical tolerance;
- pan followed by the exact inverse pan restores the original world anchor/state;
- zoom followed by its inverse around the same anchor restores the original anchor/state within tolerance;
- composing pans is equivalent to the combined translation where the model declares that property;
- changing viewport dimensions does not change the world coordinate represented by a preserved anchor unless explicitly specified;
- floor changes never silently reuse records from a different floor;
- URL serialize/parse round trips preserve declared public state;
- enabled layer state round trips through reload/history as declared.

Use deterministic generated cases. If an external property-testing library is introduced, it must support seed replay, shrinking, lockfile pinning, and a concrete benefit over a small repository-owned deterministic generator.

### 5.3 Browser integration and end-to-end tests

Playwright remains the primary browser acceptance engine.

It must cover complete real-user journeys, including combinations rather than only isolated controls:

- boot and qualification;
- map pan and zoom;
- floor and mode changes;
- coordinate navigation;
- semantic search;
- creature/NPC/monster controls;
- inspector behavior;
- reload and deep links;
- browser back/forward;
- responsive/mobile interaction;
- keyboard/touch behavior;
- failure injection;
- network/runtime error policy;
- repeated state transitions.

A Playwright test should assert the user-observable result and relevant runtime invariant, not only that an action completed without throwing.

### 5.4 Read-only renderer observability

The actual browser runtime needs a bounded diagnostic snapshot that is useful to tests and failure analysis without providing mutation powers.

Prefer extending existing truthful diagnostic surfaces when feasible rather than inventing a parallel test runtime.

A renderer diagnostic snapshot should expose only serializable read-only values that are already true in the product, for example:

- exact Atlas revision/product identities already known to runtime;
- camera/world center or authoritative camera state;
- current zoom/floor/mode;
- viewport width/height and DPR;
- monotonically useful frame/render generation identifiers where available;
- base-layer transform/matrix actually used for the last committed frame;
- per-overlay transform/matrix actually used for the same frame;
- visible chunk IDs/counts and cache counts;
- visible creature/marker stable IDs/counts and their world anchors when already known;
- last committed screen-space bounds/anchors for a bounded sample of rendered world-anchored records;
- renderer timing samples already measured by the runtime;
- animation generation/frame identity where animation is shipped.

The API must not expose setters, privileged loaders, fake records, alternate transforms, or mutable internal objects. Return frozen/copy snapshots.

Tests must not rely only on the diagnostic API for expected values. Its purpose is evidence and cross-layer comparison, not self-certification.

### 5.5 Geometry and transform verification

This is a P0 class for Atlas because multiple visual layers represent the same world coordinate system.

For every world-anchored overlay currently shipped or added later, tests must prove synchronization with the base map across relevant operations.

Mandatory scenarios include:

- horizontal pan;
- vertical pan;
- diagonal pan;
- repeated pan in both directions;
- wheel zoom;
- button zoom;
- zoom around non-central pointer anchors where supported;
- pan immediately followed by zoom and vice versa;
- viewport resize;
- mobile portrait/landscape-like resize;
- floor change;
- AUTO/MINIMAP/MAP transitions where layers remain applicable;
- enabling an overlay before movement;
- enabling an overlay during/after movement;
- enabling NPC and monster layers together;
- rapid layer toggling while map work is in flight;
- reload/deep-link restoration after movement.

For a drag/pan, record independently observed deltas. A typical assertion is conceptually:

```text
base map delta        = (-243.0, +81.0)
NPC world-anchor delta = (-243.0, +81.0)
monster anchor delta   = (-243.0, +81.0)
allowed drift          <= declared tolerance
```

The tolerance must be justified by renderer/DPR/subpixel behavior. Do not choose a large tolerance that can hide visible drift.

The known class of defect in which NPC/monster layers move independently of the map must have a permanent regression scenario.

### 5.6 Renderer/WebGL probes

Some failures are not observable through DOM bounds because the base map is WebGL/canvas based.

Use bounded deterministic probes to verify, where needed:

- expected non-empty rendering at known authoritative world regions;
- correct floor/mode selection;
- missing/blank tile detection;
- layer ordering/compositing where semantically required;
- tile/texture replacement after pan/zoom;
- no stale frame surviving a committed camera/floor transition;
- expected pixel-region identity/hash only when a stable renderer environment makes that oracle reliable.

Prefer small probes/crops to full-frame equality.

### 5.7 Targeted visual regression

Visual regression is a secondary oracle, not the primary geometry oracle.

Use it for stable surfaces such as:

- critical controls/layout;
- known map landmark crops;
- creature/NPC marker crops;
- inspector states;
- loading/error states;
- representative mobile layouts;
- renderer artifacts that are difficult to express as geometry.

Baseline policy:

- baseline provenance records exact browser container/version, viewport, DPR, locale/timezone and tested revision or intentional baseline revision;
- animations are frozen or sampled at a deterministic frame only when that is semantically valid;
- updates to baselines require an explicit reviewed change, never automatic acceptance;
- failure emits expected, actual and diff artifacts;
- broad full-page pixel gates are avoided when they are sensitive to irrelevant raster/font differences.

#### 5.7.1 Creature animation completeness

Creature animation is not proven by a working toggle, a non-zero frame counter, or one animated fixture. For a pinned animation publication, verification must combine a full published-program census with real-browser pixel evidence.

The census must validate every advertised creature program: unique presentation identity; positive phase count and geometry; phase-content cardinality; content-addressed blob existence and geometry; and, for every multi-phase program, complete supported timing metadata. Multi-phase programs must also be classified by final rendered content identity so a presentation whose phases collapse to identical pixels cannot be silently counted as visibly animated.

For the currently pinned `oteryn-atlas-animation-runtime-v1` publication (`rootContentId=sha256:413de22b245288da68153e2c0e9d4efe4ee011421b56a09532c8119829079540`), Issue #108 records the acceptance census: 1,377 creature programs; 101 multi-phase; 100 visually dynamic; and one authoritative static-equivalent multi-phase presentation, `outfit-presentation:sha256:b16bfc92e9d9e9c8f790507f987a11b25a169c4343c9d68471de76a5f3565c88`. Any change to this census requires an explicit publication/provenance update, not a relaxed assertion.

Browser qualification must separately sample at least one verified multi-phase NPC and one verified multi-phase monster/spawn. With playback OFF, capture the deterministic static creature pixels; with playback ON, require an actual creature-overlay pixel change while factual creature anchors/identity stay unchanged; after playback is disabled, require exact restoration of the static creature pixels. Merged-main live acceptance must repeat this pixel-level proof against the deployed revision.

Creature-layer pixel equality must be evaluated against the backing pixels of #creature-overlay itself and compared as decoded RGBA, not by byte equality of a DOM element screenshot. On mobile, controls/backdrops can be composited above the canvas inside the same screenshot rectangle even while the creature backing store is byte-for-byte visually restored. UI/chrome screenshots remain separate visual-acceptance evidence; they must not contaminate the animation-layer oracle.

### 5.7A User-facing visual acceptance

Targeted pixel regression and geometry/render oracles do not by themselves answer whether Atlas is usable and visually coherent as a user actually sees it. Every materially user-visible Atlas change therefore has an additional user-facing visual acceptance layer in the real browser.

Required acceptance combines two independent forms of evidence:

- deterministic usability assertions for viewport overflow, clipping, occlusion/hit-testing, reachable controls, readable visible text and a meaningful map viewport;
- exact-revision full-frame evidence captured after representative user actions and actually reviewed by a human or visual-capable agent.

Representative states include, where applicable, the initial desktop/mobile view, map plus controls and inspector, semantic search/results, selected inspector content, enabled layers, NPC/monster presentation, animation playback, explicit MINIMAP/CLASSIC/detail-mode transitions, floor changes, coordinate/zoom/pan navigation, mobile controls drawer, mobile inspector drawer, portrait/landscape-like responsive transitions, degraded optional services and required-resource fail-closed presentation. The exact primary acceptance census is versioned in `e2e/user-visual-scenarios.json` so capture, review and publication use one contract.

Full-frame evidence is not used as a fragile whole-page pixel-equality oracle. It exists so a reviewer can detect defects that technical assertions may miss: visually broken composition, awkward overlap, clipped text, bad z-order, unreadable density, blank/garbled regions, or a state that is technically valid but obviously wrong to a user. Stable Atlas-owned component/inspector/drawer crops may still use `toHaveScreenshot` as blocking targeted baselines; Game-derived map/world pixels remain review artifacts rather than committed baselines.

Each successful evidence frame must record the exact Atlas revision, target mode, browser/project, viewport, DPR, URL, bounded runtime state and screenshot digest. Full-frame evidence containing Game-derived raster pixels is retained only in the trusted local acceptance directory used for review/status publication; it is not committed as a source baseline or uploaded as routine GitHub evidence. The local exact-head E2E status publisher must refuse success unless all required frames were reviewed and an approval manifest is cryptographically bound to the exact Playwright `summary.json` and screenshot digests.

Review is an evidence step, not a checkbox loophole: the reviewer must open every required frame before approval. Automated code checks may verify the review manifest and digests, but they must not fabricate the perceptual review itself.
### 5.8 Seeded model-based interaction stress

Atlas must be tested as a stateful application, not only as isolated scenarios.

Create a small command model of legal user actions, for example:

- pan(dx, dy);
- wheelZoom(delta, anchor);
- zoomButton(direction);
- floorUp/floorDown/selectFloor;
- setMode;
- toggleOverview;
- toggleNpc/toggleMonster;
- changeNpcRole;
- search/select result;
- coordinate navigation;
- back/forward;
- reload;
- resize(viewport);
- open/close responsive drawers.

The generator must:

- use a recorded seed;
- generate only bounded sequences;
- record every action and important state snapshot;
- assert invariants after actions, not only at the sequence end;
- retain the first failing action index;
- support exact replay from seed/action log;
- shrink or minimize failing sequences where practical.

PR qualification uses a bounded fixed seed set plus regressions. Scheduled qualification uses a larger rotating deterministic seed set. Any newly discovered failure is promoted to a named permanent regression case.

### 5.9 Race and fault injection

Test the application while work is in flight, not only after everything is idle.

Applicable scenarios include:

- delayed range/chunk responses;
- reordered completion of independent requests;
- bounded request abort/failure;
- optional resource absence;
- required publication failure;
- malformed index/chunk JSON;
- stale/partial product version mismatch;
- rapid pan/zoom during data fetch;
- rapid layer toggles during fetch/render;
- resize while render work is pending;
- history/reload around in-flight operations.

Fault injection must be bounded and test-only at the network/harness edge where possible. Do not weaken product fail-closed behavior.

### 5.10 Performance and stability verification

Correct-but-janky behavior is not sufficient for an interactive map.

Collect evidence for representative heavy interactions, including where technically reliable:

- scenario duration;
- frame interval distribution / late-frame count;
- long tasks;
- render/update duration samples;
- visible/drawn record counts;
- chunk/cache counts and boundedness;
- request count/bytes for bounded viewport actions;
- JS heap or browser memory signals in stable environments;
- repeated-action growth/leak indicators.

Initial thresholds must be evidence-based. Establish a baseline across repeated known-good runs before making a budget blocking. Once a budget is accepted, regressions outside the allowed envelope fail qualification unless the budget change is explicitly reviewed with supporting evidence.

Performance tests must use normalized deterministic workloads rather than arbitrary wall-clock timing of unrelated startup noise.

### 5.11 Memory/leak and soak testing

Scheduled/full qualification should exercise bounded repeated operations such as:

- pan/zoom cycles;
- layer enable/disable cycles;
- creature search/selection cycles;
- floor/mode transitions;
- responsive resize cycles.

Compare resource/cache/heap indicators before and after a controlled workload. The goal is to detect monotonic unbounded growth, retained stale records, duplicated overlay state, and runaway cache behavior.

### 5.12 Accessibility and input verification

Preserve and expand critical interaction assertions:

- accessible names;
- truthful disabled/hidden state;
- keyboard activation/Escape where supported;
- focus behavior for critical drawers/dialog-like surfaces;
- touch-enabled mobile controls;
- no unreachable core control at supported responsive widths.

Axe or another automated accessibility engine may be added if it materially improves defect detection, but automated scans do not constitute formal WCAG conformance.

### 5.13 Mutation testing for critical pure logic

For critical pure JavaScript logic, especially coordinate transforms, state normalization, parsing and invariant-heavy reducers, scheduled mutation testing should be evaluated.

The purpose is to find tests that execute code but do not actually detect wrong behavior. Mutation testing is not required for WebGL/browser rendering paths where it is prohibitively expensive or noisy.

A mutation tool may be introduced only after a bounded proof shows useful signal, reproducibility, acceptable runtime, and pinned dependencies. Surviving mutations in critical logic become test-improvement work rather than being hidden by lowering a score.

## 6. Test completeness by change type

The table below defines applicability. It is not a user-facing module status system.

| Changed behavior | Minimum applicable verification |
| --- | --- |
| Pure calculation/parser/state logic | unit + negative + boundary + property/invariant where meaningful |
| Game/publication data contract | schema/provenance + positive/negative fixtures + integration consumer |
| URL/history/navigation | unit/contract + Playwright reload/back/forward/deep-link |
| UI control/layout | contract + Playwright user flow + responsive + accessibility; targeted visual where appearance matters |
| Map camera/pan/zoom/floor | unit/property + browser geometry invariants + WebGL/render probe + E2E |
| NPC/monster/POI/world overlay | data contract + E2E + geometry synchronization + stress; visual crop if appearance matters |
| WebGL renderer/tile pipeline | deterministic browser/WebGL proof + geometry/render probes + failure handling + performance |
| Animation | deterministic scheduler/state tests + full published-program census + independent NPC/monster pixel-change samples + browser frame/state evidence + stress + performance |
| Search/inspector | logic/contract + E2E + invalid/no-result + persistence/history |
| Cache/streaming/network | unit where possible + range/protocol contract + fault injection + boundedness/stress |
| Performance-sensitive runtime | functional tests + deterministic performance workload + regression budget after baseline qualification |
| Bug fix | permanent regression reproducing the defect + all applicable surrounding layers |

If a row does not apply to a change, it does not need to be forced in. If it does apply, omission requires explicit technical justification in the PR and cannot be silently ignored.

## 7. CI execution model

Runtime cost is managed through tiers, but changed behavior must receive its complete applicable deterministic coverage before merge.

### 7.1 Local/change-targeted

Purpose: fast development feedback.

Run affected `node:test` contracts, deterministic property cases, and targeted Playwright specs. This tier does not replace exact-head qualification.

### 7.2 PR exact-head required qualification

Required before merge:

- repository/provenance/security checks already required by policy;
- all deterministic unit/contract tests;
- full applicable Docker Playwright suite;
- geometry/render regressions for affected map/overlay paths;
- stable targeted visual regressions for affected surfaces;
- bounded seeded stress smoke set;
- accepted performance regressions for affected performance-sensitive paths;
- zero hidden retries;
- exact final head and full diff review.

The implementation should integrate these into existing required fan-in rather than create optional green badges that do not block merge.

A narrowly verified documentation-only PR is the only automatic exception to the heavy Docker Playwright requirement. The CI classifier may set `docs_only=true` only when every current changed path, and every previous path reported for a rename, is a well-formed `docs/**` path ending in lowercase `.md`. Empty diffs, mixed changes, root documentation, non-Markdown files under `docs/`, malformed paths, workflow/test/runtime/package/data changes, and any unknown classification fail closed to `requires_e2e=true`. Deterministic, provenance, security and required fan-in checks still run. `atlas-gate` may accept `verification-browser=skipped` only when classification itself succeeds with the exact pair `requires_e2e=false` and `docs_only=true`; every other pull request still requires exact-head `atlas-local-e2e=success`.

### 7.3 Full qualification

Run the complete deterministic Atlas verification matrix, including all stable geometry/render/visual probes and a broader fixed seed set. Use for major cross-cutting changes and release/live acceptance preparation.

### 7.4 Scheduled/nightly depth

Run longer but still bounded suites:

- larger deterministic stress seed matrix;
- repeated critical tests to expose flakes/races;
- soak/leak checks;
- mutation testing of critical pure logic when adopted;
- additional viewport/DPR profiles;
- additional browser/GPU variants when they correspond to supported/valuable environments.

Failures must retain replay evidence. A scheduled failure is real work even if PR gates were green.

### 7.5 Merged-main/live acceptance

Direct-preview qualification must verify the served revision exactly matches the intended merged `main` revision before success can be claimed. A stale live deployment is a failed qualification, not a pass for an older build.

### 7.6 Executable CI and nightly wiring

The repository implementation uses the existing required `atlas-gate` fan-in rather than a disconnected optional test island. `CI / verification-node` runs the deterministic Node contract/property suite. `CI / change-classification` inspects the exact GitHub pull-request file list, including rename source paths, and publishes the fail-closed `docs_only` / `requires_e2e` pair. For trusted same-repository pull requests that require E2E, `CI / verification-browser` is a lightweight GitHub-hosted evidence gate: it requires the exact pull-request head to carry an authenticated `atlas-local-e2e=success` commit status produced only after the complete Docker Playwright suite passes locally. `atlas-gate` requires classification success on every pull request and permits the browser job to be skipped only for the proven documentation-only case defined in section 7.2. The repository candidate checkout in `CI` and `Extraction Provenance` continues to use the exact pull-request head rather than GitHub's synthetic merge ref. `provenance-gate` remains a separate required branch-protection context and its pinned legacy-source checkout is unchanged.

The heavy required browser workload is temporarily assigned to the local Molehill-PC Docker execution plane rather than the slower Synology organization runner. Native Windows checkout-overlay runs bridge Docker Desktop to the LAN publication through the read-only transparent `e2e/local-publication-forwarder.py` listener on `host.docker.internal`, because direct Docker bridge access to the LAN publication is not reliable on this host. The publisher `e2e/publish-local-e2e-status.ps1` rejects a dirty tree, a remote branch that does not equal the tested HEAD, a summary whose `expectedRevision` differs from HEAD, any non-passed scenario, or any retry before it can publish `atlas-local-e2e=success`. E2E-required fork pull requests cannot satisfy this trusted same-repository evidence gate. On `main` pushes the PR-only classifier and local-evidence jobs are skipped and `atlas-gate` requires those skips while retaining all deterministic CI inputs; merged-main/live browser qualification remains a separate exact-served-revision responsibility under section 7.5.

Scheduled/manual Molehill depth uses the installed Windows PowerShell execution shell. It does not share the Synology live-acceptance concurrency group, because GitHub concurrency replaces older pending executions and could otherwise cancel a required current-main deployment. Instead the read-only depth workflow verifies X-Oteryn-Atlas-Revision against its exact github.sha immediately before browser depth and again after it; a stale publication or a live cutover during the run therefore fails closed rather than producing a false green result.

`.github/workflows/verification-depth.yml` provides scheduled/nightly depth and manual dispatch. Its bounded deterministic expansion is:

- no replay of the complete PR-required browser suite; for E2E-required pull requests the exact-head 58-scenario matrix remains the separate `atlas-local-e2e` merge gate;
- the critical geometry/framebuffer set repeated three times with retries still fixed at zero;
- stress seeds `133`, `1096043585`, `2779096485`, and `3735928559`, each with 64 replayable actions;
- opt-in `nightly-desktop-dpr2` and `nightly-tablet` Chromium profiles;
- stable performance, visual, accessibility, race/fault and soak/leak specs when those worker-delivered files exist at the exact revision; absent categories are recorded in `optional-depth-skips.json` with an explicit reason rather than silently ignored;
- the existing deterministic property test that kills controlled sign/scale coordinate mutants. A third-party mutation framework is not adopted until it demonstrates bounded additional signal.

Required browser runs publish `summary.json`, `results.json`, HTML/test-result evidence and `failure.json` on failure. Nightly uploads each phase under a separate bounded artifact directory, including any action logs, performance/visual evidence emitted by the specs, and the explicit optional-depth applicability record. Workflow artifacts are retained for 14 days.

Concrete local equivalents are:

```text
node --test tests/animation-runtime.mjs tests/browser-semantic.mjs tests/deployment-policy.mjs tests/gui-contract.mjs tests/npc-markers.mjs tests/pixel-store.mjs tests/semantic-search.mjs tests/semantic-search-creatures.mjs tests/synology-live-workflow.mjs tests/fullworld-layers/*.test.mjs tests/fullworld-runtime/*.test.mjs tests/properties/*.test.mjs tests/verification/*.test.mjs
ATLAS_PUBLICATION_ORIGIN=http://192.168.1.2:8097 ATLAS_E2E_WORKERS=1 ./e2e/run.sh
```

## 8. Browser/GPU matrix

Use two complementary environments:

1. reproducible pinned containerized Chromium for deterministic CI and main E2E;
2. real hardware-browser qualification where available for GPU/driver/render issues that software rendering may not expose.

Do not require every browser merely because Playwright supports it. Add Firefox/WebKit or additional Chromium channels when they represent supported targets or provide demonstrated differential-test value.

For hardware runs, record browser version, OS, GPU/driver identity when available, viewport/DPR, exact Atlas revision, and whether hardware acceleration was actually active.

## 9. Failure artifact contract

Every browser/stress/render failure must produce a compact machine-readable manifest that points to bounded evidence.

Recommended per-run structure:

```text
artifacts/e2e/<run>/
  summary.json
  results.json
  failure.json                 # when failed
  action-log.json              # seeded/model sequence when applicable
  renderer-before.json         # when applicable
  renderer-after.json          # when applicable
  performance.json             # when applicable
  visual/
    expected.png
    actual.png
    diff.png
  test-results/
    ... Playwright trace/video/screenshot/error context ...
  html-report/
```

`failure.json` should include applicable fields such as:

- scenario/test id;
- Atlas SHA and target URL/mode;
- browser/container identity;
- viewport/DPR;
- deterministic seed;
- first failing action index;
- camera/floor/zoom/mode before and after;
- expected and observed base/overlay deltas;
- measured drift/tolerance;
- first bad frame/generation when known;
- console/page/network failure census;
- links/relative paths to trace/video/screenshots/visual diff;
- performance budget and observation when relevant.

The format exists specifically so humans and automated agents can diagnose a failure without reconstructing the whole run from prose.

## 11. Required first regression: overlay/map drift

The first geometry regression must reproduce and permanently guard the defect class where NPC and monster layers move independently from the base map during pan/zoom.

The regression must:

1. load an authoritative location with at least one published world-anchored creature/marker;
2. enable NPC and monster layers as applicable;
3. capture base and overlay screen/world evidence before movement;
4. perform a deterministic drag;
5. wait for the committed render generation, not an arbitrary sleep;
6. capture evidence after movement;
7. independently calculate/compare movement deltas;
8. fail on drift above a justified small tolerance;
9. repeat with at least one zoom interaction and a combined pan+zoom sequence;
10. retain before/after state and screenshots on failure.

A test that only asserts `drawnRecords > 0`, toggle state, or absence of console errors does not satisfy this regression.

## 12. Coverage census and reporting

Each full run should emit a machine-readable scenario census containing at least:

- scenario id/name;
- category (`unit`, `contract`, `e2e`, `geometry`, `render`, `visual`, `stress`, `performance`, `accessibility`, `failure`);
- target mode;
- browser/profile;
- pass/fail/skip;
- duration;
- seed when applicable;
- artifact paths on failure.

This is execution evidence, not a manually maintained product/module status dashboard.

Skipped tests require a machine-readable reason. A feature that is required on the tested target must not be silently reclassified as optional merely to keep the suite green.

## 13. Change review rules

For implementation PRs:

- review whether tests assert behavior or only presence;
- inspect whether expected values come from an independent oracle;
- inspect all broad allowlists/tolerances/timeouts for hidden failures;
- reject arbitrary sleeps when an observable ready/committed condition exists;
- reject enlarged visual/geometry tolerances without evidence;
- reject tests that mock away the integration being claimed;
- reject skipped required coverage without an explicit blocker;
- reject bug fixes without a regression when the bug is reproducible;
- preserve first-failure evidence;
- rerun exact final head after any test or implementation change.

## 14. Rollout order

Implementation should proceed in this order because each step improves the diagnostic value of the next:

1. freeze the repository testing policy and artifact schema;
2. inventory current suites and normalize scenario reporting;
3. add read-only renderer observability;
4. implement independent geometry oracle and NPC/monster drift regression;
5. add coordinate/transform property tests;
6. add seeded action runner and fixed stress smoke seeds;
7. add targeted render/WebGL probes;
8. add stable targeted visual baselines only for surfaces with good signal;
9. establish repeatable performance workloads and collect baseline distributions;
10. enforce accepted performance budgets;
11. add scheduled longer stress/soak/flakiness depth;
12. evaluate bounded mutation testing for critical pure logic;
13. integrate all applicable deterministic gates into required CI fan-in;
14. qualify exact final head and then exact merged-main live preview.

Each rollout step must itself be tested before it is trusted as a gate.

## 15. Definition of done for the platform implementation

The platform implementation is complete only when:

- repository agent policy requires deep applicable tests with every shipped change;
- the existing `node:test` and Playwright systems are extended, not duplicated;
- renderer observability is read-only and verified not to alter product behavior;
- geometry invariants permanently catch NPC/monster/base-map drift;
- coordinate/zoom/floor/state property tests are deterministic and replayable;
- seeded interaction stress is reproducible and retains action/seed evidence;
- stable targeted visual regression exists where it provides independent signal;
- WebGL/render probes cover cases DOM geometry cannot prove;
- performance workloads are reproducible and accepted budgets are evidence-backed;
- failure artifacts are machine-readable and diagnosis-oriented;
- no required failure is hidden by retry, broad allowlist, large tolerance, arbitrary skip, or stale-target qualification;
- applicable verification is part of required exact-head CI fan-in;
- a full exact-head run passes;
- the final diff is reviewed and required `atlas-gate`, `provenance-gate`, and applicable security checks pass;
- merged-main/live acceptance is performed only against the exact served merged revision.

The long-term rule is simple: Atlas behavior that ships must remain executable, reproducibly tested behavior.
